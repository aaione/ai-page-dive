## 二、新 Findings

### [minor] R3-m1 — newChat 落在 pending（提取）窗口内：旧 send 的 cancelled 回调把「已取消」气泡注入全新会话

- **证据**：App.tsx:269-294（`onStartResult` 无条件向当前 stream 追加错误气泡）+ App.tsx:313-316（`beginSession` 清场但无法阻止在途 sendMessage 回调）+ sw.ts:448（提取完成后 `currentTask` 已易主 → 返回 `{error:'cancelled'}`）。
- **触发路径**：点「总结」→ 数秒提取窗口内点「新对话」（beginSession 已清空消息）→ 提取完成 → SW sendResponse `{error:'cancelled'}` → 面板回调 `onStartResult` → 全新空会话首屏常驻一条「已取消」错误气泡（且 `done:true`）。新用户首体验路径（发了又反悔是高频操作）。
- **修法**：`onStartResult` 的 `cancelled` 分支在 `s.pending === false`（本轮已被 beginSession/newChat 清场，非本轮回调）时静默丢弃——或 beginSession 记 epoch，回调携带并比对。一行级。

### [minor] R3-m2 — HistoryView 点击条目后 host 读失败零反馈：点击无反应且可反复无声失败

- **证据**：HistoryView.tsx:39-49（listener 只消费 history-list/history-file/deleted/delete-fail，**无 `case 'error'`**）+ stdio.ts:103（`history-read` 失败回 `error` 帧 code `read-fail`）+ :27（pendingPathRef 已置但 viewing 永不出现）。
- **触发路径**：历史条目对应文件被外部删除/权限变化 → 点击条目 → pendingPathRef 置位、无 history-file 回帧、read-fail error 帧无人消费 → UI 停留在列表页毫无反应；再点其它条目仍正常（pendingPathRef 被覆盖），但用户对首次点击「按钮坏了」无从归因。Settings 有同款 error 消费（Settings.tsx:139-143），HistoryView 缺席。
- **修法**：listener 增补 `error` + `code==='read-fail'` 分支：清 pendingPathRef + 顶部一次性提示「该记录读取失败」。

### [minor] R3-m3 — Settings 的保存/删除在 SW 死亡或 port 僵死窗口内完全静默（callback 丢弃 ok:false）

- **证据**：Settings.tsx:207-214（saveWorkflow 的 sendMessage callback 为 `() => void chrome.runtime.lastError`，不检查 `resp.ok`）+ sw.ts:246（`nm` 转发在 `nmPort.send` 返回 false 时回 `{ok:false}`，无 error 帧）+ Settings.tsx:91-92（list 同样静默）。
- **触发路径**：SW 被回收/崩溃（host 断连的 `__host-disconnected` 会把整个面板换成 Onboarding，覆盖大半场景——但 SW 死亡时面板不卸载）或 port 对象存在但 postMessage 同步抛错的毫秒窗（nmport.ts:81-86）：用户点「保存」→ 无 workflow-saved、无 error 帧、无任何提示。模式列表为空时仍可「新建模式」编辑（Settings.tsx:299 不看 host 状态），编辑数分钟后保存无声失败 = 未保存编辑静默丢失。
- **修法**：所有 `{t:'nm'}` 发送的 callback 检查 `resp?.ok === false` → `setHostError('本机组件未连接，操作未执行——请重开面板重试')`。三处（save/delete/reveal）一行级。
- 附注（归入 F11/R2-i11 已知家族的放大面）：host 断连时 App 整体切换 Onboarding（App.tsx:359）会把**含未保存编辑的 Settings 瞬间卸载**，dirty 确认缺失在「host 崩溃」路径上同样成立。

### [minor] R3-m4 — 面板本地校验错误被冠「本机组件返回错误：」前缀——文案与行为偏差

- **证据**：Settings.tsx:196（空正文守卫用 `setHostError('正文为空或尚未加载完成，未保存——…')`）+ Settings.tsx:284-287（渲染统一拼「本机组件返回错误：{hostError}」）。
- **触发路径**：已有/新建模式清空正文 → 点保存 → 提示显示为「**本机组件返回错误**：正文为空或尚未加载完成，未保存…」——这不是 host 错误，是面板本地校验；用户被误导去怀疑本机组件/重装。
- **修法**：hostError 增加 `local` 标记（或拆两个 state），本地校验不走 host 前缀。R2-M2 修复引入该守卫时复用了 hostError 通道，d39cbce 未纠。

### [minor] R3-m5 — Onboarding stuck 横幅显示期间再次复制：计时已重置但横幅不消失

- **证据**：Onboarding.tsx:55-61（`copy()` 刷新 `copiedAtRef` 但**无 `setStuck(false)`**）+ :34（探测循环只在计时超 90s 时置 true，不清除）。
- **触发路径**：stuck 横幅「复制命令已超过 1 分半仍未生效」显示中 → 用户按提示重新复制命令 → `copiedAtRef` 归零重计，但横幅继续常驻且文案声称「已超过 1 分半」——与已重置的计时矛盾（文案与行为零偏差清单项）。F8 修复只给「立即检测」按钮加了重置，漏了 copy 路径。
- **修法**：`copy()` 的 then 分支补 `setStuck(false)`。一行。

### [info] R3-i6 — 终局错误气泡拼接英文原始 message：「已取消: task cancelled」

- **证据**：App.tsx:240（`${ERROR_LABEL[m.code] ?? m.code}: ${m.message}`）+ task.ts:132/223/352（host 固定发英文 `'task cancelled'`）。
- 触发路径：任务运行中点「停止」→ 气泡显示「已取消: task cancelled」——code 已有中文映射（ERROR_LABEL），后半段英文原文对普通用户是噪音；同类还有「任务超时: …」「CLI 输出异常: …」。
- **修法**：code 命中 ERROR_LABEL 时只显中文标签，原始 message 收进 `title` 供悬停/排障。

### [info] R3-i7 — 流式正文输出期间头部状态标签停留在「思考中…」

- **证据**：SummarizeView.tsx:360-364（`running && msg.streaming` 时显示 `phase`）+ App.tsx:183（phase 仅由 task-status/task-alive 更新，**首个 text chunk 不清 phase**）。
- 触发路径：claude `--include-partial-messages` 流式期（thinking→deltas）——正文已在逐字流出，头部仍标「思考中…」；30s 后被 task-alive 改写为「处理中（已 Ns）…」部分缓解，30s 内不一致。
- **修法**：task-chunk 分支在追加文本后 `phase: ''`（已有正文即不再称思考中）。

### [info] R3-i8 — beginTurn 的 `{...BLANK}` 连 finished 台账一并清空，F9 的拒收窗口随每轮发送重开

- **证据**：App.tsx:300-308（beginTurn 展开全 BLANK，`finished` 未像 beginSession/resumeHistory 那样显式携带）。
- 时序推演：newChat 后旧任务尾巴帧若晚于用户下一次 send 到达，则该帧不在（已清空的）finished 中且 `taskId===null` → 首帧绑定放行。当前 FIFO + 人类操作时序下窗口为毫秒级（host 的 cancelled 终局帧先于用户可再次发送到达）**实际不可达**，但与 F9「跨会话拒收」的修复意图存在语义缺口；若未来引入 host 拥塞/重连重放则成真洞。
- **修法**：beginTurn 同 beginSession 显式 `finished: s.taskId ? [...s.finished, s.taskId].slice(-8) : s.finished`。一行，与 F9 对齐。
