## Findings

### F1（major）`__host-disconnected` 不清 pending：追问轮 spawn 窗口断连 = 输入锁死 120 秒且零反馈

- 位置：`apps/extension/src/sidepanel/App.tsx:279-291`
- 触发路径：追问轮 send → SW `startFollowUp` 同步返回 `{ok:true}`（回调即结束，之后无任何兜底回调）→ 在 host 发出首帧（`task-status: spawned`，CLI spawn 需数秒）之前 host 进程崩溃/被杀 → SW `nmPort.onDisconnect` 转发 `__host-disconnected` → 该 handler 只 `activeId:null` + 给 **streaming 中**的气泡盖错误。此时面板态是 `pending=true, activeId=null, messages=[用户消息]`——没有任何 streaming 气泡，`messages.map` 是 no-op：
  - 错误提示：**一个都不显示**；
  - `pending` 未清 → `running` 恒 true → 输入框持续 disabled、按钮持续显示「停止」；
  - 用户点停止：`cancel` → SW `cancelCurrent` 经 respawn 的新 port 发 `task-cancel`，host 不认识该 taskId（`stdio.ts:78-80` 对未知 taskId 静默无帧）→ 无终局；
  - 唯一出口是 120s 看门狗，且文案是误导的「响应超时」——用户明明刚看到过连接中断却无气泡、也无法重试（输入被锁）。
- 注：首轮总结不受此影响（SW 在提取前同步下发 `task-status: reading`，`activeId` 已建、气泡存在，能盖上错误）；唯一漏洞在追问轮无占位帧的 spawn 窗口。
- 建议修法（三行级）：handler 中追加 `pending:false` + `taskId` 记入 `finished` + 在无 streaming 气泡时也注入独立错误气泡（与 `onStartResult` 的滤空占位 + 错误气泡同构）：
  ```ts
  setStream((s) => ({
    ...s, done: true, activeId: null, pending: false, taskId: null,
    finished: s.taskId ? [...s.finished, s.taskId].slice(-8) : s.finished,
    messages: [
      ...s.messages.map((m) => m.streaming ? { ...m, streaming: false, error: '本机组件连接中断——请重试发送', isError: true } : m),
      // 无 streaming 气泡（pending 窗口）时兜底注入：
      ...(s.messages.some((m) => m.streaming) ? [] : [{ id: `d${Date.now()}`, role: 'assistant' as const, text: '', error: '本机组件连接中断——请重试发送', isError: true }]),
    ],
  }))
  ```

### F2（minor）`task-done` 是唯一缺 `finished` 台账守卫的终局 handler：旧任务迟到 done 会收掉新任务的 streaming 态

- 位置：`apps/extension/src/sidepanel/App.tsx:218-226`
- 触发路径：任务 A 在跑 → 用户点「新对话」（`beginSession` 把 A 记入 `finished`，SW 侧 cancel）→ 立即发送任务 B → B 的占位气泡 streaming 中 → A 的 `task-done` 迟到（CLI 恰在取消瞬间正常完结）→ handler 先走 `s.taskId !== m.taskId` 分支，把**所有** streaming 气泡 `streaming:false`——B 的活跃气泡被误收尾。后果：B 继续流式追加文本但思考指示/光标永久消失（`task-chunk` 不会恢复 `streaming:true`）、复制/下载动作条在流中途提前出现。对照同文件 `task-chunk`（:181）、`task-alive`（:197）、`task-status`（:209）、`task-error`（:260）均有 `finished.includes` 前置拒收，唯独 `task-done` 没有——状态机一致性死角。
- 建议修法：handler 首行加 `if (s.finished.includes(m.taskId)) return s`（与其余四个 handler 对齐）；或 mismatch 分支不动他任务气泡。
- 佐证：窗口窄（新对话后秒级内旧任务恰好完结），后果为表现层降级而非锁死，定 minor。

### F3（minor）附件跳过提示延迟到下一次发送才可见：选择当下零反馈

- 位置：`apps/extension/src/sidepanel/SummarizeView.tsx:162-184`（`pickAttachments` 设 `attachNotice`）与 `:133-134`（仅在 `send()` 时以 `beginTurn` 入列展示）
- 触发路径：用户一次选 7 个文件（或单文件 >512KB）→ chips 只显示 5 个（或 0 个）→ **当下无任何提示**告知哪些文件被丢、为何被丢——提示要等用户点发送后才以一条「用户气泡」的形式出现。若用户接着就发送，还行；若用户在挑选后继续编辑输入（常见：附上代码文件后补充提问），被静默丢弃的附件在发送前始终不可知，与 r4-ux「静默丢弃 = 用户不知道附件没带上」的修复初衷只完成了一半。附带：该提示以 user 角色气泡呈现（用户并未说过这句话），且永久留在会话记录里。
- 建议修法：`pickAttachments` 即时渲染提示（chips 区域内联一行 `已跳过：…`，或轻量 toast），`attachNotice` 不再随 `send` 注入用户消息轨。

### F4（minor）panel-ready 重试耗尽后永久停留「正在连接本机组件…」，无超时出口

- 位置：`apps/extension/src/sidepanel/App.tsx:107-121`（重试 2 次：500ms/1s，耗尽后 `return` 保持 `hostOk=null`）
- 触发路径：SW 冷启动慢于 1.5s（低配机/系统繁忙/扩展刚更新）→ 面板永久停在 loading 文案，无重试按钮、无轮询——用户唯一出路是收起再重开面板。对照 Onboarding 自带 3-15s 自动轮询 + 「立即检测」按钮，loading 态反而是全产品唯一无自愈出口的状态。`chrome.runtime.sendMessage` 唤醒 SW 通常可靠，故概率低，但一旦命中即是死屏。
- 建议修法：耗尽后降频继续轮询（如 5s），或在 loading 文案旁给「重试」按钮（复用 `ping()`）。
